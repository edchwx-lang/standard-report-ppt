# V6.3 Blueprint Deconstruction: Visual Reverse Compiler Design

**Status:** approved direction; implementation not started  
**Branch:** `codex/v6.3-visual-reverse-compiler`  
**Base:** `v6.2.2-stable-reconstructed` / `d3c9103841e59e50de801a472055b49758ddb4a6`  
**Validation blueprint:** S3 (Chinese toy-industry slide)  

## 1. Objective

V6.3 replaces the post-lock deconstruction interpretation with a visual reverse
compiler. Its job is to reproduce the locked blueprint body as faithfully as
possible using editable PowerPoint primitives, while retaining only tightly
cropped non-native visuals as images.

The target is the quality demonstrated by the S3 pilot:

- the blueprint body is the highest visual authority;
- text, numbers, tables, charts, connectors, and basic geometry are editable;
- photos, complex logos, maps, and illustrations may be local crops;
- a map crop contains no labels, dots, or connectors that can be rebuilt as
  editable objects;
- no generic grid, card, or palette substitution is allowed when it changes the
  blueprint's visible composition.

## 2. Hard scope boundary

V6.3 changes only `construction_mode: deconstruct` after the formal blueprint
has been byte-locked.

| Area | V6.3 treatment |
| --- | --- |
| Source intake, research, authoring, evidence | Frozen |
| ImageGen prompt and invocation | Frozen |
| Design draft and formal blueprint bytes | Frozen |
| Blueprint locking and provenance | Frozen |
| `construction_mode: bitmap` review, crop, build, audit, acceptance | Frozen |
| Deconstruction visual review after lock | Replace with V6.3 census + scene graph |
| Windows deconstruction compiler | Upgrade, primary implementation |
| macOS deconstruction compiler | Best-effort mapping of the same scene graph |
| Packaging format and delivery contents | Preserve |

V6.3 must not add fields that change pre-blueprint cache keys. The runtime
revision is recorded only in post-lock deconstruction artifacts and the
post-lock cache payload.

## 3. Authority model

### 3.1 Master-owned skeleton

The five existing shapes on slide 1 of `assets/company_template.pptx` are the
only authority for:

1. chapter;
2. page title;
3. core judgment;
4. source;
5. page number.

The compiler opens or clones the template slide, preserves those shape objects,
and changes text only. It must not recreate, move, resize, recolor, or restyle
them. Font family, font size, paragraph settings, fills, borders, margins, and
geometry remain inherited from the template. Body coordinates are derived from
the free area between the template skeleton regions.

### 3.2 Blueprint-owned body

Within the body region, the locked blueprint is the highest visual authority for:

- module boundaries and proportions;
- object position and size;
- color, stroke, corner, and spacing;
- z-order and overlap;
- chart appearance;
- labels and relationships;
- selection of images, illustrations, icons, and logos.

Canonical content remains a factual guard for conflicting numbers, dates,
units, proper nouns, and sources. It is not a license to redesign the body.

## 4. Post-lock pipeline

The deconstruction path becomes:

1. verify immutable blueprint and template hashes;
2. identify the five template-owned skeleton shapes and derive the body ROI;
3. create full-body and overlapping review tiles;
4. write an independent visual census from the blueprint pixels;
5. write an atomic scene graph and reconcile it against the census;
6. extract only approved local crops from the locked blueprint;
7. normalize the scene graph for the selected platform without changing its
   visual meaning;
8. compile the whole deck once;
9. render and run structural/editability/crop audits;
10. if necessary, perform at most one targeted body reconstruction pass;
11. accept and cache the valid PPTX, or deliver the second structurally valid
    result with explicit visual warnings.

No step may regenerate or repaint the blueprint.

## 5. Independent visual census

The old self-declared alignment inventory is insufficient: an omitted logo or
photo cannot be detected if both the alignment and page spec omit it. V6.3
therefore introduces `.build/v63_visual_census.json`, produced directly from
the full body image and overlapping review tiles before the scene graph is
accepted.

Each candidate contains at least:

```json
{
  "candidate_id": "S03-C042",
  "kind": "logo",
  "bbox_px": [1308, 443, 1410, 481],
  "parent_candidate_id": "S03-C039",
  "review_tile_ids": ["B03", "B04"],
  "expected_treatment": "crop",
  "confidence": "high"
}
```

The census is independent in the following enforceable sense:

- it is bound to the locked blueprint hash and body ROI hash;
- it is created before scene-graph reconciliation;
- every candidate must resolve to one or more scene elements, one crop asset,
  or an explicit ignorable-decoration reason;
- the scene graph may not silently reduce the census count;
- missing text, data, logo, photo, chart, table, connector, or material geometry
  is a hard prebuild blocker.

Decorative texture or negligible anti-aliasing may be ignored. Materiality is
defined by visible meaning or visible composition, not by a minimum object size.

## 6. Atomic scene graph

V6.3 introduces `.build/v63_scene_graph.json`. It is body-only and uses
blueprint pixel coordinates as the source coordinate system. The compiler maps
those coordinates to the template-derived body ROI.

Supported atomic families are:

- `text` with runs and paragraph properties;
- `rect`, `round_rect`, `ellipse`, and `freeform`;
- `line`, `connector`, and `arrow`;
- `chart_group` with editable visual primitives such as bars, lines, markers,
  axes, labels, and donut segments;
- `table_group` with editable cells and text;
- `image_crop` for approved non-native subjects;
- `group` for hierarchy and z-order only.

Every atomic element contains a stable ID, source pixel box, z-order, group or
parent, style, content, reconstruction mode, and source census IDs. Semantic
labels such as `flow`, `matrix`, or `donut_chart` remain metadata; they do not
authorize a generic renderer to replace the observed layout.

### 6.1 Rendering rules

- Body colors are sampled or transcribed from the blueprint. A fixed blue-gray
  palette may not replace the observed body palette.
- Charts are rebuilt as editable PowerPoint shapes by default because visual
  fidelity is the priority. Native PowerPoint chart objects are optional when
  they reproduce the blueprint without visible loss.
- Regular tables may use native PowerPoint tables; irregular tables use
  editable cell primitives.
- Simple icons and pictograms are recreated with shapes or freeforms when
  feasible.
- Complex logos, photos, maps, and illustrations may remain image crops.
- Map labels, markers, and connectors are separate editable elements even when
  the map base is cropped.
- No `body_asset`, whole-body crop, or mixed text-and-graphics crop is allowed.

## 7. Crop contract

Every image crop is extracted from the locked blueprint and records:

- one unique `asset_id`;
- tight `source_px` and exact target box;
- `subject_count: 1`;
- no editable text, except lettering intrinsic to a logo/brand mark;
- no native geometry that should be reconstructed;
- no complete panel/frame perimeter;
- no outline in the final PPTX;
- one scene-graph insertion and one census resolution.

Declared, extracted, compiled, and inserted asset IDs must match one-to-one.
Photos and logos are not optional decoration when they materially appear in the
blueprint.

## 8. Windows implementation

Windows remains PowerPoint COM and is the release-quality route. The existing
PowerPoint session, master inheritance, save, render, and packaging mechanisms
are retained. The V6.3 body renderer is added alongside the legacy component
renderer and is selected only for post-lock deconstruction.

The Windows renderer must support:

- exact pixel-to-slide coordinate transformation;
- per-run text formatting and editable text boxes;
- editable lines, arrowheads, rounded rectangles, ellipses, and freeforms;
- editable donut/ring segments and chart primitives;
- explicit z-order and stable shape names;
- local crop placement with no outline;
- preservation of the five existing master placeholders.

Legacy high-level renderers such as `matrix`, `flow`, and `text_card` remain for
older revisions but are not the default V6.3 visual compiler.

## 9. macOS implementation

macOS consumes the same census, scene graph, crop manifest, and authority rules.
`python-pptx` remains the backend; there is no technology rewrite.

The Mac adapter maps supported atoms to OOXML/python-pptx equivalents. Platform
normalization may adjust syntax but may not redesign the page. A backend
limitation must be reported explicitly. It must not silently convert editable
text, data, or basic geometry into a picture.

Because native macOS PowerPoint is unavailable in the current environment,
V6.3 Mac acceptance is limited to:

- scene-graph normalization tests;
- PPTX/OOXML structure tests;
- editability and crop-contract tests;
- successful headless generation where supported.

The release record must say `mac_native_render_unverified`; Windows validation
is not evidence of Mac rendering parity.

## 10. Quality, speed, and stopping policy

Quality controls are separated into hard structural blockers and ordinary
visual warnings.

### Hard blockers

- missing census candidate or unresolved material object;
- missing/garbled selected text or data;
- editable-class content rasterized into an image;
- undeclared, missing, duplicate, or stale crop;
- whole-body or mixed-region screenshot;
- broken topology or connector relationship;
- invalid/blank render or corrupt PPTX;
- altered blueprint hash or altered template skeleton contract.

### Warnings

- small spacing or alignment differences;
- minor font-rendering differences;
- anti-aliasing or low-frequency pixel variance;
- ordinary color-sampling variance;
- small crop-edge variance that does not include other objects.

After the first build, the comparison generates a targeted delta list. At most
one body-only reconstruction pass is allowed. The second structurally valid
build is delivered even if ordinary visual warnings remain. The workflow must
not enter repeated check/rebuild loops.

## 11. S3 acceptance contract

S3 is the final Windows integration test. Acceptance requires both a visual
review and an object ledger proving at least the following:

- the five skeleton items are the original template placeholders with text-only
  changes;
- two main body panels and all section bars preserve the blueprint layout;
- both growth-value cards, editable numbers, CAGR label, and arrow exist;
- three regional cards, three province labels, three descriptions, three photo
  crops, and the China map crop exist;
- three map dots, connectors, and labels are editable;
- the donut/ring and center pictogram are editable shapes;
- TOP10/27.2%, company names, and shares are editable;
- LEGO, POP MART, TOPTOY, BLOKEES, 52TOYS, ROLIFE, X11, and FINDING UNICORN
  marks are present as approved crops or faithful editable marks;
- all three company tiers, headers, labels, dividers, and footnote are present;
- no full-slide or full-body bitmap exists;
- no duplicate image, accidental overlap, untrimmed frame, or text omission is
  visible.

The successful pilot render is a diagnostic reference, not a shortcut asset.
The V6.3 run must compile S3 through the real post-lock path.

## 12. Release and rollback

Implementation remains on `codex/v6.3-visual-reverse-compiler` and is not
installed globally or pushed during development. Promotion occurs only after:

1. frozen-boundary tests pass;
2. bitmap regression tests pass unchanged;
3. Windows unit/integration tests pass;
4. the real S3 Windows run satisfies the acceptance contract;
5. Mac structural tests pass with the native-render limitation disclosed.

Rollback is the V6.2.2 base commit. The earlier local
`codex/v6.3-deconstruction-runtime` candidate is retained for reference but is
not merged into this branch.
